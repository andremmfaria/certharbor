## Corrections to the plan

- **E2E-AUTH-11's `Max-Age=-1`.** That is the Go-side `http.Cookie.MaxAge` value. `net/http` serialises any negative `MaxAge` as `Max-Age=0` with a 1970 `Expires`, so the assertion is against the wire form.
- **The issuance form field is `name`, not `cert_name`** (`handlers/certs.go`). Nothing in the plan states it, and a wrong field name reaches the "Please fill in all fields" branch, which renders inline at 200 rather than redirecting.
- **Flash messages are one-shot.** Any test that checks status and then re-fetches to read the flash consumes it on the first fetch.
- **E2E-HLTH-05's session claim is half right.** The plan says sessions "come back on the next request once postgres is healthy, without a re-login". `rejectSession` clears `s.Values` and Saves, which overwrites the client's cookie, so a session *used* during the outage is dead for good. A session left untouched through the outage does come back. The test now pins both halves.
- **E2E-HLTH-06's row is named `CA URL` on the page**, not `Step-CA API`. The latter is the check's name in `handlers/health.go` and the name E2E-ADM-07's preflight list uses. `/admin/integrity` also renders two tables, and only the second carries status badges.
- **Error text is HTML-escaped in rendered pages.** `validateIdentifier`'s `%q` quotes arrive as `&#34;`, so E2E-CERT-03 compares the escaped form.
- **E2E-BAK-01's `step-ca-data.tgz` keeps a bare `config/` entry.** Section 2.7.5's calibration says `config/` is absent; the directory header is written before the read that fails, so the entry is there with nothing under it. `secrets/`, which sorts after it, is never reached. The test asserts contents, not entries.
- **`manifest.json`'s `components` is an array** of `{name, path, size, sha256, status}`, not an object keyed by name.
- **A stopped container's compose DNS name stops resolving**, so E2E-ADM-03's "dial-level error" arrives as `lookup step-ca ... server misbehaving` rather than `connection refused`.
- **OpenSSL 3 prints DNs as `CN = x`**, older builds as `CN=x`. The host and the harness image disagree, so `helpers/openssl.ts` normalises before any assertion.
- **E2E-BOOT-07 (d)'s empty list is not fatal.** The plan listed an unset and a malformed `TRUSTED_PROXY_CIDRS` as two fatal sub-cases. Only the malformed one exits, and the entry in `plans/e2e-tests.md` now says so.
- **`/ready` carries the certificate keys.** The body is `status` plus `backendCert`, `backendCertNotAfter`, `webCert` and `webCertNotAfter`, so E2E-HLTH-02 asserts exactly those five keys and the boot-fingerprint assertions match on the subset. E2E-HLTH-02 dials `BACKEND_URL`, since it asserts the backend's own body.
- **E2E-RENEW-01's log strings changed with the renewer.** One loop now renews both leaves, so the lines are `TLS leaf auto-renewer started`, `leaf renewed` and `leaf renewal failed, will retry`.

## Local run

`.env` needs `WEB_HOSTNAME`, which is nginx's `server_name` and the only name it completes a handshake for, and `PUBLIC_BASE_URL`, `SESSION_SECURE=true` and `HOST_IP=127.0.0.1` besides. The `secrets/*` files needed `chmod 644`: they were mode 600 owned by uid 1002, while step-ca runs as uid 1000 and certharbor as uid 10001, so both were denied. The backend publishes no host port, so the projects run from the harness image on `step-network` the way `e2e.yml` does, with `BASE_URL=https://certharbor-console:8443` and `BACKEND_URL=https://certharbor:8443`. That also gives per-test rate-limit isolation. A host run needs a `WEB_HOSTNAME` that resolves on the host, and the `infra` project is the one that runs on the host.

## The React and OpenAPI-client question, and a deviation it caused

The React/OpenAPI-client replacement question was answered (see `plans/frontend-backend-split.md`): the split is going ahead, and Phases 0 to 3 are complete. This track was never actually paused on that decision: `1574eab` landed the three OIDC `api` specs and, more consequentially, all four `ui` companions on 2026-10-16.

**Survives unchanged.** Everything the `api` project asserts about status codes, headers, redirects, database rows, the CA's log, issued certificate material and the backup bundle. That is the bulk of what is written so far: RBAC, CSRF, certificates, history, security log, admin console, backup, health, static MIME and traversal, and the session-revocation family.

**Needs rewriting.** Every assertion that reads rendered HTML: the content substrings in E2E-RBAC-01's 200 cells, flash-message text, `extractCSRF`'s hidden-input scrape, the row parsers in the history, security-log, provisioner and integrity specs. A React client would move these to JSON responses, which is a smaller and more stable oracle, but the assertions themselves would be rewritten.

**Changes shape entirely.** CSRF as a hidden form field (E2E-CSRF-01, -05) and the inline logout form (E2E-AUTH-11) are properties of server-rendered forms. An OpenAPI client would carry the token differently, or use a different mechanism altogether.

**Unaffected either way.** The whole Section 3.1 bootstrap matrix, the TLS and renewal work, and the compose, workflow and harness infrastructure. None of it touches the presentation layer.

**Deviation: the four `ui` companions were written, and at the wrong time.** `plans/frontend-backend-split.md` Section 10 says `ui` specs are written last, after Phase 8, once the React markup is stable, on the reasoning that they would otherwise be the first thing thrown away. They were written anyway, in `1574eab`, against the server-rendered markup the split plan's Phase 9 deletes: `cert-01.ui.spec.ts`, `auth-04.ui.spec.ts` (covering both E2E-AUTH-04 and E2E-AUTH-07), `auth-11.ui.spec.ts` and `cfg-01.ui.spec.ts`. Consequence: those four files must be rewritten, or retired, in whichever of Phases 4 to 8 replaces the page each one asserts against. Until then they guard the legacy server-rendered UI only, not anything the split is building toward. The SPA specs that Phase 3c added (`spa/spa-shell.ui.spec.ts`) are the first `ui` specs written against the new markup, and the only `ui` specs CI runs.

**Phase 8/9 closeout (2026-11-13).** `plans/frontend-backend-split.md`'s Phases 0 through 9 are all complete (Phase 9, the template/static-serving removal, merged as PR #59, commit `fcd08f5`). Everything above this entry that still talks about server-rendered markup, `h.render`/flash messages, hidden-input CSRF scraping, or the four "legacy" `ui` specs flagged in the deviation note above is historical record of how coverage was built across that transition, not the current state: the template routes it describes no longer exist on `main`.

The one e2e gap Phase 8 itself had left open — a full browser-level spec for the profile/MFA flow (enroll via QR, confirm, see recovery codes once, disable with dual reauth) — is now written and merged: `test/e2e/specs/profile/mfa.ui.spec.ts`, E2E-MFA-01 to -04 (`plans/e2e-tests.md` Appendix A, 83 → 87), PR #62, squash commit `144e5cd`. Before Phase 8 this existed only as Go integration-test coverage (`profile_mfa_integration_test.go`), never exercised through the real browser/QR/TOTP path end to end.

Running it live against a real stack (not just typechecked, since sandboxed CI-shaped environments can't bring up docker) surfaced two real, previously-shipped bugs that no prior test caught, both fixed in the same PR:
- `backend/handlers/totp_api.go`'s `buildTOTPQRPNG` double-base32-encoded the TOTP secret before rendering the QR (`GenerateOpts.Secret` base32-encodes whatever bytes it is given; passing an already-base32 string's bytes re-encodes it into a different, longer one). Every QR-code-based MFA enrollment enrolled an authenticator app against a secret the server would never validate; only the manual-entry-key path worked. `TestBuildTOTPQRPNG_SecretRoundTrips` is the regression guard — the old tests asserted a valid, differently-sized PNG came out, never that the embedded secret matched the input.
- `frontend/src/api/authEndpoints.ts`'s `AUTH_ENDPOINTS` allowlist was missing `POST /api/v1/profile/mfa/disable`. Its 401 (wrong current password, a legitimate reauth-check value) was being treated by the global interceptor as session expiry, clearing cache and redirecting to `/login` before the component's own error handling could render.

Live numbers from that same verification pass, against a real four-container stack run inside `step-network` matching CI's harness-container invocation exactly (not the GitHub-hosted runner itself, a local rebuild of the same images and the same `docker run --network step-network ... certharbor-harness:e2e` command CI's `e2e-main suite` job runs): `api` project 200/210 passing, 7 skipped, the remaining 3 failures were nginx `limit_req`/`limit_conn` self-trips from zero-latency local docker-to-docker networking hitting the generic CSRF/RBAC sweeps' tight request loops faster than CI's own network timing does (same default `WEB_RATE_LIMIT=20r/s`/`WEB_RATE_BURST=40` CI uses, confirmed not product bugs); `ui` project 33/36 passing, with the 3 failures pre-existing and unrelated to MFA/QR/the interceptor fix: `auth-04.ui.spec.ts`'s long-known missing `TWOFA_SUBJECT`/`twofa_user` fixture (see the deviation note above — still not fixed, still out of scope), and `cert-01.ui.spec.ts`/`cfg-01.ui.spec.ts`'s dependency on seed certificate data that a bare fresh stack does not create. PR #62's actual CI run on GitHub Actions (`e2e main suite` job) was separately green before merge.

An independent gap audit (read-only, no code changes) done alongside this closeout found the e2e suite still has **zero functional coverage** (beyond the generic RBAC/CSRF role-and-auth sweeps) for: all 11 ACME routes (issue, list, get, renew, delete, autorenew-toggle, settings, events — the single biggest gap), temporary-users CRUD (3 routes), admin notifications (3 routes), and the self-service password-reset flow (`/password-reset/requests|validate|confirm`, 3 unauthenticated routes — distinct from the admin-initiated `/users/{id}/password-reset`, which auth-sessions.api.spec.ts does cover). This is scoped as a follow-up phase, not yet started.
