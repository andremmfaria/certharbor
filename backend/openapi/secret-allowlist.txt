# Property names the spec-scanning test would otherwise reject, one per line.
#
# Every entry must be writeOnly: true and absent from every response schema,
# which the test asserts rather than trusting. An entry here is a deliberate
# decision that a secret-shaped name may appear in a request body, never in a
# response.
#
# This file carries a CODEOWNERS entry: adding a line is the one edit that can
# quietly move a secret into the contract.
#
# The auth and profile domains add their request-body fields as they are
# ported.
password

# Phase 4 (plans/frontend-backend-split.md Section 6): the manual-path/
# scan-import request body for POST /api/v1/certificates/import/paths
# carries the filesystem location of a certificate and key to import.
# Section 6 specifies these exact field names; the response-side
# equivalents in GET /api/v1/certificates/import-candidates are
# deliberately named certFile/keyFile instead, which do not match this
# file's regex, so they stay unrestricted plain response data.
certPath
keyPath

# Phase 6 step 1 (plans/frontend-backend-split.md Section 6, 8): the
# password-reset action of the old POST /admin/users multiplexer becomes
# POST /api/v1/users/{id}/password-reset, whose request body names the
# field newPassword. The exact-match lookup below needs this as its own
# line; the "password" entry above covers only properties named exactly
# "password".
newPassword

# Phase 6 (plans/frontend-backend-split.md Section 6): PATCH
# /api/v1/admin/notifications' SMTP password field. 5.8: secret fields are
# writeOnly, absent from the response, and absent on write means
# unchanged — never a PUT, so the first save of an unrelated field cannot
# clear it.
smtpPassword

# Phase 7 step 3: PATCH /api/v1/acme/settings' Cloudflare API token and
# Route53 secret access key. Same 5.8 guarantee as smtpPassword above:
# writeOnly, absent from the response, and absent on write means
# unchanged.
cfToken
r53SecretKey

# Phase 8 step A: POST /api/v1/profile/change-password's current-password
# field, required to reauthorise the change. writeOnly, absent from the
# response. newPassword above already covers that request's new-password
# field.
currentPassword

# Phase 8 (plans/frontend-backend-split.md Section 8 "Phase 8. Profile and
# MFA", Section 6): POST /api/v1/password-reset/validate and /confirm both
# carry the raw reset token in the request body rather than as a path
# parameter or query string (so it never lands in a problem document's
# "instance", a route-templated metric, or a trace label). It is bearer
# credential-shaped for the 30-minute TTL it is valid, writeOnly, and never
# appears in any response.
token

# Phase 8 step B (plans/frontend-backend-split.md Section 8 "Profile and
# MFA"): POST /api/v1/profile/mfa/disable's current-password field. Same
# exact-match reasoning as newPassword above: the "password" line only
# covers a property literally named "password".
currentPassword

# Phase 8 step B: POST /api/v1/profile/mfa/enrollment/confirm's recovery
# codes. Unlike every other entry in this file, these genuinely are the
# response: they are shown once, in plaintext, and never again (the DB only
# ever stores bcrypt hashes). writeOnly:true here is a deliberate departure
# from this file's usual "never in a response" guarantee — see
# backend/api/profile_mfa.go's comment on confirmMfaEnrollmentBody.
recoveryCodes
